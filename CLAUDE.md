# CLAUDE.md — Goszakup Analytics

Личный инструмент анализа рынка госзакупок Республики Казахстан.
**Общение с пользователем — на русском.**

## Цель продукта

Найти ниши **товаров**, в которые относительно легко зайти новым поставщиком —
в первую очередь то, что можно импортировать (например, из Китая) и перепродавать
государству. Инструмент должен собирать данные с портала госзакупок, нормализовать
их и выдавать аналитику: что закупается регулярно, кто выигрывает, где низкая
конкуренция, куда есть смысл заходить.

Это **инструмент лично для владельца**, не SaaS. Ни аутентификации, ни пользователей,
ни организаций, ни тарифов, ни мультитенантности строить не нужно.

## Scope: что анализируем

**Три приоритетные категории (можно расширять смежными):**

1. **Спортивные товары и инвентарь** — мяч (футбольный/баскетбольный/волейбольный),
   коньки, тренажёр, ракетка, сетка, татами, спортивное оборудование, спортивный инвентарь
2. **Медицинские расходные материалы** — шприц, перчатки, бинт, маска, катетер,
   система инфузионная, бахилы, тест-полоски, расходный материал
3. **Техническое оборудование** — камера, видеокамера, объектив, прожектор,
   светодиодный свет, микрофон, микшер, видеосервер, студийное оборудование,
   оборудование для видеосъёмки, телевизионное оборудование
   (в т.ч. закупки АО «Хабар» и аналогичных телеорганизаций)

**Категорически вне scope:** одежда, уголь, нефть, топливо, стройматериалы
(если не относятся к трём категориям выше), **услуги**, **работы**.
Интересуют только товары, которые можно физически поставить.

**Обязательные фильтры при сборе:**
- Вид предмета закупки = **Товар** (не услуга, не работа)
- Способ закупки = **Открытый конкурс** и другие открытые конкурентные способы
- Только успешно заключённые, действующие или исполненные договоры.
  Отменённые закупки не учитывать.

## Какие данные собираем по каждому договору

| Поле | Источник |
|---|---|
| Наименование товара | предмет договора |
| Количество | предмет договора |
| Цена за единицу | предмет договора |
| Общая сумма договора | карточка договора |
| Дата заключения | карточка договора |
| Заказчик | карточка договора |
| Поставщик | карточка договора |
| Способ закупки | карточка договора |
| Номер договора | карточка договора |
| Первоначальная (начальная) цена | объявление/лот, если доступно |
| Итоговая цена и % снижения | вычисляемое |
| **Марка / товарный знак, модель, тип** | техническая спецификация |
| **Страна происхождения** | техническая спецификация |
| **Завод-изготовитель** | техническая спецификация |

Если поля нет — писать явно **«Нет данных»**. Никогда не додумывать и не заполнять
правдоподобными догадками: это аналитика для реальных денежных решений.

## Техническая спецификация — обязательна в MVP

Путь на портале:
**Реестр договоров → номер договора → Предметы договора → ID → документ «Техническая спецификация»**

Из документа извлекаются три поля (марка/модель, страна происхождения, завод-изготовитель).
Пример того, как это выглядит в реальном документе:

```
Счетчик для холодной воды
Марка: ЭКО НОМ, Модель: СВ 15-110
Страна происхождения: Россия
Завод-изготовитель: ООО «ДЮКС», Россия, Москва
```

Это **самая дорогая и самая хрупкая часть проекта**: документы бывают PDF, DOC/DOCX
и сканами. Нужен пайплайн: скачивание вложения → извлечение текста → OCR для сканов →
LLM-извлечение трёх полей. Точность здесь никогда не будет 100% — храни рядом с
извлечённым значением ссылку на исходный документ, чтобы можно было перепроверить вручную.

## Итоговая аналитика, которую должен выдавать инструмент

1. Общие выводы по рынку
2. ТОП-20 перспективных товаров
3. ТОП-20 активных поставщиков
4. ТОП-20 активных заказчиков
5. Что закупается регулярно каждый год (повторяемость)
6. Высокая стоимость при малом числе участников
7. Где наименьшая конкуренция
8. Самые привлекательные категории для входа нового поставщика
9. Практические рекомендации: с каких товаров начинать

По каждой категории отдельно: средние цены, диапазон цен, признаки монополизации,
сложность входа, пригодность для импорта из Китая.

Объём важен: несколько примеров — не аналитика. Нужен массив данных, достаточный
для статистически осмысленных выводов.

## Источник данных — РЕШЕНО: скрейпинг публичного портала

**Официальный API не используем.** Проверено: `ows.goszakup.gov.kz` (REST-эндпоинты
`/contract`, `/lots`, `/trd-buy`, `/subject`, `/plans`, `/rnu`, `/refs`, `/journal`;
курсорная пагинация `page=next` + `search_after=<id>`, по 50 записей; GraphQL-схема
на `ows.goszakup.gov.kz/help/v3/schema/`) — но **анонимного доступа нет**, Bearer-токен
выдаёт Минфин РК по заявке с обоснованием. Токена нет.

Держи это в уме как **запасной путь**: если токен когда-нибудь появится, метаданные
лучше брать из API, а скрейпингом добирать только файлы техспецификаций.

## Проверенные факты о портале (добыты дорого — не переоткрывать)

Хосты:
- `goszakup.gov.kz` — публичный фронт (RU), `satypalu.gov.kz` — казахская версия
- `v3bl.goszakup.gov.kz` — рабочее веб-приложение (личный кабинет, вход: `/ru/user/`)
- `old.goszakup.gov.kz` — архив старого портала
- `ows.goszakup.gov.kz` — API (нужен токен)

Технические особенности (получены при работе с порталом через код):
- **ОПРОВЕРГНУТО: публичные реестры НЕ блокируют простые HTTP-клиенты.**
  Обычный curl/httpx получает 200 на поиске лотов, реестре договоров, карточках
  договоров, вкладках объявлений и POST-эндпоинтах. Браузер, сессия, keep-warm
  и привязка к User-Agent для сбора не нужны. Утверждение про 403 верно только
  для страниц личного кабинета (`/ru/cabinet/`, `/ru/myapp`) — оно пришло из
  проекта `goszakup_confidential` и к публичным реестрам не относится.
- **ОПРОВЕРГНУТО: ~1 с на запрос — не потолок.** Замер: 10 параллельных потоков
  дают устойчивые **35 запросов/с без единой ошибки** (47 601 объявление за 22 мин).
  Тяжёлые страницы (2000 записей, 2.7 МБ) — да, ~12 с. Клиент в `gz/client.py`
  сам сбавляет темп при отказах, поэтому параллелить безопасно.
- **Приложение на CodeIgniter**, сессия в cookie `ci_session`, включён
  `sess_match_useragent` — сессия жёстко привязана к User-Agent. Если работаешь
  с сессией, клиент ОБЯЗАН слать тот же реальный `navigator.userAgent`, иначе 302 на логин.
- **TTL сессии короткий: ~5–11 минут простоя.** Для долгих прогонов нужен keep-warm
  (периодический запрос по живому эндпоинту).
- **Ошибки приходят как `200 OK` + JSON `{"status":"error","message":"..."}`**,
  а не как 4xx. Проверять только HTTP-статус НЕДОСТАТОЧНО — нужно парсить тело.
- Часть листинговых страниц кабинета (`/ru/cabinet/`, `/ru/myapp`, `/ru/application/list`)
  отдаёт 403 при обращении не из браузера, тогда как другие страницы того же
  приложения отдают 200. Ожидай неоднородного поведения по эндпоинтам.

## Открытые вопросы — СНЯТЫ 2026-07-27

Все четыре блокирующих риска проверены реальными запросами. Не переоткрывать.

1. **Реестр договоров доступен без авторизации — ДА.**
   Правильный URL — `goszakup.gov.kz/ru/registry/contract`. Записанный ранее
   `/ru/search/contracts` не существует и всегда отдаёт «Доступ запрещен»;
   это была ложная тревога, а не запрет доступа.
2. **Техспецификации скачиваются без ЭЦП — ДА.** PDF берётся обычным curl,
   без cookies. Но см. ниже: нужных полей в них нет.
3. **Актуальные данные — на основном портале**, `old.goszakup.gov.kz` не нужен.
   Поиск лотов покрывает 2016–2026, фильтр по годам полный (сумма по годам
   сходится с общим итогом).
4. **Фильтр «краткое содержание договора» — ЕСТЬ, но только под авторизацией.**
   Анонимная и авторизованная формы реестра — разные. Под логином на
   `v3bl.goszakup.gov.kz/ru/egzcontract/cpublic` (POST + csrf) доступны
   `filter[description]` (краткое содержание), `filter[enstru_code]`,
   `filter[supplier_innbin]`, `filter[customer_innbin]`, `filter[subject_type]`
   (буквенный: G=Товар, R=Работа, S=Услуга).
   **Автоматизировать нельзя:** cookie сессии HttpOnly, в скрипт не переносится.
   **И не нужно:** замер показал ~600 договоров по слову «мяч» против 9 004 лотов
   через публичный поиск лотов — краткое содержание часто generic
   («Товары согласно техспецификации»), а поиск лотов идёт по наименованию
   и описанию лота, то есть по товарному уровню.
   Само поле краткого содержания достаётся публично из карточки договора.

## Факты, добытые 2026-07-28 (не переоткрывать)

**Техспецификация поставщика — найдена.** Это «Приложение 17 к конкурсной
документации», заполняет его поставщик отдельно по каждому лоту, формат — HTML,
двуязычный (сначала казахская таблица, следом русская). Внутри есть всё нужное:
«Наименование товара с указанием марки», «Страна происхождения»,
«Завод-изготовитель», плюс год выпуска, гарантия и ГОСТ.

- **Сам файл скачивается анонимно** по `https://v3bl.goszakup.gov.kz/files/download_file/{a}/{b}/`
  — ни cookies, ни ЭЦП не нужны.
- **Но ссылку на него отдаёт только авторизованный `v3bl`**: путь
  `v3bl/ru/egzcontract/cpublic/units/{cid}` → клик по «Ид» → секция «Техническая
  спецификация». Анонимно `v3bl` отдаёт 302, а публичный `goszakup.gov.kz`
  тот же `loadunit` возвращает без секции документов.
- Проверено и не сработало: публичный `loadunit`, `registry/show_plan`,
  вкладки объявления `documents`/`lots`/`result`/`contracts`.
- Документ сам себя идентифицирует: поля «№ конкурса» и «№ лота» совпадают
  по формату с `lots.announce_id` и `lots.lot_number` — привязка идёт по
  содержимому, имена файлов не важны.

**Протоколы итогов открытого конкурса — публичны и очень полезны.** Вкладка
`?tab=protocols` даёт 2–3 ссылки `download_file`. Формат — **HTML, не PDF**
(модуль, написанный под PDF ЗЦП, их молча пропускал). Дают по каждому лоту:
«Информация о представленных заявках на участие в конкурсе (лоте): N»,
«Отклоненные заявки: N», «Допущенные заявки: N» и списки поставщиков с БИН.
Это единственный публичный источник реального числа участников.

**Карточка договора** `/ru/egzcontract/cpublic/show/{cid}` анонимно даёт
дату заключения, вид предмета закупок (Товар/Работа/Услуга), фактический
способ закупки и краткое содержание.

**НДС в предметах договора.** В таблице `cpublic/units/{cid}` колонка «Сумма»
идёт с НДС у плательщиков НДС и без — у остальных (замер: 191 договор из 358
ровно ×1.12, 119 ровно ×1.0). Сравнивать цены по ней нельзя — цену без НДС
надо брать из карточки позиции (`loadunit`), там она подписана явно.

**Открытый конкурс — узкая, но самая денежная полоса:** 358 договоров против
56 919 лотов ЗЦП, но 7.4 млрд из 12.3 млрд тенге всей выборки.

## Технические требования к реализации

- **Сбор:** реальный браузер (Playwright/chromedp) или браузероподобный HTTP-клиент.
  Обязательны: rate limiting, вежливые паузы, повторы с backoff, устойчивость к обрыву
  на середине (возобновляемость).
- **Сырые данные сохранять как есть** (HTML/JSON/файлы) отдельно от нормализованных.
  Перепарсить из локального кэша должно быть возможно без повторного похода на портал.
- **Документы:** PDF/DOC/DOCX/сканы → текст → OCR при необходимости → LLM-извлечение.
- **Экспорт:** Excel/CSV обязательно (это основной формат потребления аналитики).
- **Дедупликация и нормализация:** названия заказчиков/поставщиков пишутся
  по-разному — нужна нормализация по БИН, а не по строке названия.

Стек не выбран — решить в начале работы и зафиксировать здесь.

## Чего НЕ делать

- Не строить аутентификацию, роли, организации, биллинг — инструмент личный.
- Не долбить портал параллельными запросами: он медленный и легко отдаёт 403.
- Не выдумывать данные. Отсутствует поле — «Нет данных».
- Не расширять scope на услуги и работы, даже если они попадаются в выдаче.
